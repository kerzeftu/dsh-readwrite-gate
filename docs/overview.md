# 项目概览

`@local/dsh-access-permission` 是 DeepSeek Harness（DSH）的一个 Cordis 插件 bundle。
它给 Harness 增加两件原本没有的能力：

1. **两级新的权限档**——“无权限”（什么都看不到、改不了）和“工作区内读写”（工作区与临时目录里可读可改，出了这个范围要用户点头），并保留原有三档，组成五档阶梯。
2. **读写分开的授权**——模型要碰工作区之外的文件时，弹一次授权页，用户可选“不允许 / 仅一次 / 该对话中总是可以访问（或修改）”。读的授权不附带写，写的授权也不附带读。

## 为什么需要它

DSH 自带的文件沙箱只围栏**写**：`mode: read-only` 拦所有写，`workspace-write` 拦工作区外的写，
`danger-full-access` 不拦。读侧默认不设防——模型的 `read`/`grep` 可以读整块磁盘。
权限预设也只有三档（只读 / 工作区可写 / 完全访问），表达不了“只能看工作区内”和“什么都别碰”这两种中间态。

这个插件补的正是这两块：**读围栏**由插件自己实现，**两档新语义**通过扩展预设表实现，写侧继续交给平台沙箱。
两个围栏叠加的结果是：插件管“该不该做”，平台管“做不做得到”。

## 五档一览

| 权限档 | 预设 id | 读 | 写 | 平台沙箱 |
|--------|---------|----|----|----------|
| 无权限 | `no-access` | 什么都不给读（除非本对话授权过该路径） | 全拒 | `read-only` |
| 工作区内读写 | `workspace-access` | 工作区 + 临时目录；以外逐次授权 | 工作区 + 临时目录；以外弹页后仍被沙箱拒绝 | `workspace-write` |
| 只读 | `read-only` | 任意路径 | 全拒 | `read-only` |
| 工作区内编辑 | `workspace-write` | 任意路径 | 工作区 + 临时目录；以外逐次授权 | `workspace-write` |
| 完全访问 | `danger-full-access` | 任意路径 | 任意路径 | `danger-full-access` |

五档按“给多少”排序，但**不是嵌套集合**：只读能读全盘却一个字都不能改，工作区内读写能改工作区却读不到别处。
细节见 [levels-and-scopes.md](levels-and-scopes.md)。

## 术语

- **级别（level）**：插件内部的 `full` / `workspace` / `none`，决定某一族（读或写）是否受限。
- **范围（scope）**：`readScope` / `writeScope`，取值 `anywhere` / `workspace` / `none`，说明这一族允许到哪里。
- **工作区（workspace root）**：当前会话的工作目录，由平台 `sandboxPolicy.resolve()` 给出（本机是 `~`）。
- **临时区（temp area）**：`/tmp` 与 `os.tmpdir()`，平台沙箱在可写模式下本来就放行，插件把它视为“内部”。
- **额外路径（extra path）**：本对话在级别之外额外允许的路径（面板里那两框），可随时移除。
- **opaque 命令**：路径已无法从命令文本里推断的命令（脚本、未知程序），按运行目录判定。
- **授权页**：复用系统问题面板的对话框，三选项，读写分开。

## 不做什么

- 不替换平台沙箱，也不试图绕过它；插件只做“决策”，真正的写入仍由沙箱围栏。
- 不新增模型可见工具；授权动作只属于用户。
- 不接管宿主的 `/permission` 之类命令；级别切换仍走宿主自己的权限菜单行为（本插件接管的是**控件**，不是命令）。
- 不做跨进程持久化：授权是对话内的内存状态，重启 Harness 后重新询问（见 [authorization.md](authorization.md)）。
