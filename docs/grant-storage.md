# 授权存储维护

司门默认只在当前 Harness 进程中保留授权。需要在重启后恢复时，由部署者确认存储边界，再按[配置说明](configuration.md#选择授权存储后端)启用持久化。升级不会把旧进程中的内存授权或聊天记录导入存储；需要保留的例外应重新由用户确认。

## 启用前检查

1. 确认司门的存储域 `readwrite_gate_grants` 最终路由到哪个后端。可通过 `dsh --profile <name> --dump-config` 核对域路由和 `grantPersistence`，但配置能加载不等于存储已经隔离。
2. 确认会话工具不能直接或间接修改后端数据、连接凭据或路由配置。默认后端符合条件就复用；否则由部署者注册独立的受保护后端。不能确认时，保留默认内存模式。
3. 确认后端支持原子替换单条记录，不让两个 Harness 实例同时写同一 profile 的授权数据。迁移或备份前，应先停止该 profile 的写入。

## 部署验收

在独立测试 profile 中，用自建的无敏感测试文件和“工作区内读写”档位验证：

1. 对工作区和临时目录外的测试文件选择“总是可以访问”，并另加一条手动读白名单。用 `/access-allow list` 确认两条记录。另用不同位置的文件检查“仅一次”不会出现在列表中。
2. 重启 Harness，打开**原对话**，确认两条记录已恢复。新建对话和分叉不应看到这两条；由原对话派发的子会话可继承，但不能替原对话撤销。
3. 在原对话撤销持续授权并重启，确认该条没有恢复，而手动白名单仍在。再执行 `/access-allow clear` 并重启，确认白名单也不再恢复。检查时使用不被其他授权覆盖的路径。
4. 在一次性测试后端中验证故障提示。读取失败不应恢复旧授权；保存失败不应报告添加或撤销成功。不要在生产存储上模拟故障。

## 故障、迁移与回滚

- **撤销报错**：当前进程不再使用该对话的额外授权，但先前成功保存的记录可能还在。不要把故障当成已撤销。若必须在修复前重启，先禁用持久化；修复后在隔离的测试环境核对旧记录，确认并执行需要的撤销，再恢复使用。
- **搬迁 profile 或更换路由**：记录按 profile 目录与对话 ID 区分，更换目录后不会自动找到原记录。仅改变路由也不会复制后端内容。不要手工改写记录或将旧记录覆盖到后端；旧备份可能恢复已经撤销的授权。无法确认迁移结果时，从空存储开始，让用户重新授权。
- **退回内存模式**：移除 `grantPersistence: protected-backend` 后重启；这不会删除后端记录。日后重新启用时仍须检查旧记录，不要假定它们已被清空。

[测试说明](testing.md)列出自动化覆盖范围。Linux、Windows、macOS 的存储矩阵通过，说明插件和对应版本的宿主存储组件能协同工作；实际 profile 的隔离、桌面问答和升级仍需按上述步骤验收。
